# The bench

Four specialist seats, run as a **sequential pipeline with full artifact context handed forward**, never a parallel panel and never a summary. Each seat owns one artifact contract, one template, one lane manifest, one audit duty, one write zone and a baseline runtime. The master skill owns the process (engagement types, phases, routing, gates, launcher caps); [`devcraft/CLAUDE.md`](../CLAUDE.md) owns the law (public/private split, how never what, the boundary rule, Claude plans and Codex codes, the never-do list); these files own the craft. Authored on the Devcraft build map's **Author the four-seat bench** ticket (2026-10-11) from the bench-composition and plugin-routing briefs (ratified 2026-10-08), the never-do list (rule 9), the seat-isolation probes (2026-10-10) and the five seat-contract rulings (2026-10-11).

| # | Seat | Produces | Baseline | Write zone | Audits |
|---|---|---|---|---|---|
| 1 | [Build Planner](build-planner.md) | Build plan | Opus 5.5, Claude Code | the engagement folder only | Code change + change note (Builder) |
| 2 | [Builder](builder.md) | Code change + change note | Codex GPT-6.1 Sol High | the worktree, minus test paths, Release's ops paths and controls | Release plan + runbook (Release) |
| 3 | [Verifier](verifier.md) | Test suite, written first, + run record | Opus 5.5, Claude Code | test paths only, plus the run record | Build plan (Planner) |
| 4 | [Release & Reliability](release-reliability.md) | Release plan + runbook, with the drill record | Opus 5.5, Claude Code | the plan's flagged ops paths, plus the release plan and runbook | Test suite + run record (Verifier) |

**One closed audit cycle: Planner → Builder → Release → Verifier → Planner**, the arrow reading "audits". Every audit is a fresh-context invocation over artifacts only, on the auditor's own baseline. With the plan audit fixed to the Verifier and the code audit fixed to the Planner, this is the only four-seat cycle in which the Builder never audits the tests that judge its own code. No seat co-signs.

**Running order on a full build:** Planner drafts → Verifier audits the plan → plan gate → Verifier writes the whole suite and records it failing → Builder builds, slice by slice → Planner audits the change while Release drafts on the stable diff → Builder audits the release plan → Verifier's final run → Release audits the test record → release gate → Sean's dated yes → merge, in a session Sean is driving. A small direct ask takes only the release gate, and only when it touches live data, a migration or anything that runs unattended. An ops-only direct ask runs Release → Builder's audit → release gate (see [Release & Reliability](release-reliability.md)).

**The coordinator makes every commit.** No seat runs `git commit`. The Builder's Codex pass cannot, and a Claude seat's commit fails at the pre-commit hook, which reads the machine's name list that every seat's sandbox denies by design. So a seat stages its own paths by name and gives the commit message in its exit, and the coordinator commits: a Builder slice as `<eng> S<n>`, and a Verifier or Release change with the staged index unchanged under that pass's context (`DEVCRAFT_CONTEXT=<eng>/trace/logs/pass-NN.context.json DEVCRAFT_SEAT=<seat> git commit -m "<the seat's message>"`). Under the seat's context the hook checks every path against that seat's zone, runs the secret and name scans, and stamps the `Devcraft-Seat:` trailer the diff check reads. Ruled by Sean on SWCB #133 (2026-10-13).

**The gates are not seats.** The plan gate (anchor: the build plan) and the release gate (anchor: the release plan; it attacks the change, the test record and the release plan together) run on Codex, pinned, read-only, because Claude writes both anchors. The extra security pass fires only on a plan that rates its surface high; its anchor is the code change, so it runs on a fresh-context Opus 5.5. A gate FAIL that moves an anchor's last writer to the other vendor moves the gate too, and the coordinator says so at the gate. The launcher holds the rule: every gate names its anchor (`seat.py context --anchor`) and runs on the vendor that did not last write it, read from the anchor's `model:` line (SWCB #126). All three run per the shared [protocol](../../craftwork/templates/red-team-protocol.md) and Devcraft's gate schedule ([../templates/gate-schedule.md](../templates/gate-schedule.md)). The trace kit files them as the gate seats `plan-gate`, `release-gate` and `security-pass` so their records have lanes; they hold no seat file.

**What an invocation carries:** the seat file below, the [seat preamble](../templates/seat-preamble.md) verbatim, the lane manifest, the declared target (the build's worktree and branch), the upstream artifacts in full, and the target repo's `AGENTS.md`. Never the drafting conversation. The coordinator launches every pass; no seat launches another.

## Launch forms

Both forms were proven on 2026-10-10 and are recorded in [the runtime registry](../../craftwork/templates/runtime-registry.md) (rows 2 and 3, the isolation paragraphs). Values in angle brackets are per pass.

- **Claude seats** (Planner, Verifier, Release, and the security pass; row 2): `claude -p --output-format stream-json --verbose --model claude-opus-5-5 --permission-mode acceptEdits --setting-sources "" --settings <seat settings> --strict-mcp-config --plugin-dir <seat plugin> --tools "Read,Write,Edit,Bash,Glob,Grep,Skill" --append-system-prompt-file <worktree>/AGENTS.md --add-dir <worktree> --add-dir <engagement folder> --add-dir devcraft/lanes --add-dir devcraft/corpus --add-dir <the pass's scratch folder> --max-budget-usd <cap> "<prompt>"`. `stream-json`, not `json`, since 2026-10-12: it is the live log the launcher's caps watch, and it stamps every message with its model, which rung-0 line 11 reads (`json`'s one result names the model only as a key, so line 11 could not verify it). The security pass runs read-only, without `Edit` and with a `Write` that reaches only its scratch folder (SWCB #148), and the launcher files its final answer as its findings. Never `--bare` (it drops the login) and never `--safe-mode` (it ignores the plugin). The **seat plugin** is a folder holding `.claude-plugin/plugin.json` and a `skills/` of links to exactly the skills the seat's toolbelt names, never a whole marketplace plugin, which brings its hooks. The **seat settings** file is generated per pass by `devcraft/hooks/seat.py claude-settings` into `~/.config/devcraft/passes/<engagement>/`, outside every repo: the seat's path denies, the sandbox and Devcraft's guard. `--setting-sources ""`, not `local`, because `local` still loads a `.claude/settings.local.json` planted in the repo (2026-10-11). No Task tool, so no sub-agent can start.
- **Codex seats and gates** (the Builder, the plan gate, the release gate; row 3): `CODEX_HOME=<codex seat home> codex exec --json --model <model> -c model_reasoning_effort="high" -p <eng>-pass-NN --strict-config -c web_search="disabled" -C <worktree> -o <engagement folder>/<artifact path> "<prompt>"`, never `--ignore-user-config`, which throws the seat config away, and never `--sandbox`, which silently replaces the pass profile. Pin `<model>` from the seat file or gate default: `gpt-6.1-sol` for the Builder and, since 2026-10-12, for the plan and release gates too (#99 for the Builder; Sean's re-ruling of every studio's default gate on SWCB #118). `-o` is the artifact's own path (the change note, the audit of the release plan, gate findings), never a log the coordinator copies; the JSONL on stdout is captured as `trace/logs/pass-NN.jsonl`. The pass profile (`-p`, written by `devcraft/hooks/seat.py codex-pass` into `~/.config/devcraft/passes/<engagement>/` and linked from the seat home) is the sandbox: the Builder's extends `:workspace` with test paths, Release's ops paths and controls read-only; a gate's extends `:read-only`; both deny credential files, employer paths and `held-out/` (2026-10-11). The **Codex seat home** holds its own sign-in (one `codex login` by Sean, never a link to the personal auth file) and the proven seat config: features `apps`, `plugins`, `remote_plugin`, `multi_agent`, `memories`, `browser_use`, `computer_use`, `in_app_browser`, `image_generation`, `goals` and `skill_mcp_dependency_install` off, and `[skills] include_instructions = false`, so a seat reads its skills by the paths its toolbelt gives; plus `shell_snapshot` off and a `shell_environment_policy` that strips credential variables, and Devcraft's guard as its one trusted hook (`seat.py codex-home` writes it all). Never `codex review` (ruled by Sean on [#123](https://github.com/seanwinslow28/SWCB/issues/123), 2026-10-12): it hands the work to a built-in helper, prints no meter and writes no file the pass names, so the gates run on `codex exec` like every Codex pass, with a review skill read by path. Sub-agent tools survive every switch, so a spawn is caught from the logs, never prevented: after every Codex pass `seat.py launch` saves its session files beside its JSONL as `pass-NN.rollouts/` (the same `tracekit.codexlog collect`), and rung-0 line 11 fails a pass that started a helper.
- **A pass on the other vendor** takes that vendor's form above, never a third: a gate or verification pass moved to Claude takes the security pass's read-only Claude form; a Claude seat's redraft or verification pass on Codex takes the Codex form, pinned to `gpt-6.1-sol` (the gate default) with a pass profile for its seat: `:read-only` but for Release's redraft, which writes only its ops paths. The context names the record that moves it, and the launcher reads the vendor from that record ([hooks README](../hooks/README.md#how-a-pass-is-walled), step 2; SWCB #126).

Every form runs through `seat.py launch`, never by hand: it adds the scrubbed environment, closes stdin (`codex exec` otherwise waits for piped input to append to the prompt), and kills the pass at 100% of its caps ([hooks README](../hooks/README.md#how-a-pass-is-walled), step 4).

Claude Code's built-in skills stay listed under every form. A seat's **Never** list covers them too.

## Baselines, families and the ladder

Every `model:` line names a ruled row of the runtime registry: three seats on `claude-opus-5-5` (judgment-heavy, and Release's work is the hard-to-undo actions), the Builder on `codex gpt-6.1-sol high` (Claude plans, Codex codes, so code and its tests always come from different vendors). Sean ratified the Builder-only ruling on #99 (2026-10-11), and on 2026-10-12 moved the shared escalation target and every studio's default Codex gate to GPT-6.1 Sol too (SWCB #118). The Builder and the gates now share a model; the vendor rule still holds, because each gate's anchor is Claude-written. The config default never chooses a pass's model.

Escalation follows [craftwork § Model delegation](../../craftwork/law.md#model-delegation), with one Devcraft brake: **the Verifier never escalates onto Codex.** Its ladder is Opus 5.5 → stop and ask Sean, so tests are never written by the vendor that writes the code (ruled by Sean, 2026-10-11). The Builder's ladder is the registry's: `high` → `xhigh` → stop and ask Sean, never `ultra`. The `xhigh` step runs through the launcher like any pass: `seat.py context --effort xhigh --escalation <the gate FAIL or ledger entry>` ([hooks README](../hooks/README.md#how-a-pass-is-walled), step 2; SWCB #135). A Claude seat's redraft one tier up runs on Codex through the same flag: `--escalation <record>` puts the Planner's or Release's redraft on `gpt-6.1-sol` at `high`, and the next step, `xhigh`, takes a ledger entry that names it. A verification pass runs on the vendor that did not write the repair (`--verify <repaired artifact>`), read-only; the Verifier's verification pass after a Planner repair changes no test, so it runs on Codex like any other (SWCB #126).

The trace kit's registry numbers group seats by family, one family per seat so a model never earns one seat on another's work: `build-planner` → *build planning*, `builder` → *coding*, `verifier` → *test design*, `release-reliability` → *release engineering*, and the three gate seats → *gate* (`craftwork/trace/tracekit/registry.py`, `SEAT_FAMILIES`).

## Exits every seat may take

A seat that cannot finish stops with one typed reason in its artifact header, and the coordinator routes it. Every seat: **Blocked: budget** (90% of any budget), **Blocked: architecture call** (a product or architecture call found mid-build; never-do 10), **Blocked: instruction in content** (never-do 13). The Builder adds **Blocked: spec and tests conflict**; Release adds **Blocked: needs source**.
