# The wall

The machine layer of Devcraft's never-do list ([`devcraft/CLAUDE.md`](../CLAUDE.md), rule 9): the sandbox and permission settings every seat pass runs under, the guard hook on top of them, and the git hooks on every build worktree. Built on the Devcraft build map's **Build the never-do hooks and sandbox config** ticket (2026-10-11), from the never-do ticket's wall column and that day's probes of both vendors.

The order of trust is fixed. **The OS sandbox is the wall**; the permission deny rules sit beside it; **the guard only adds sight** the first two lack (which seat is running, a path after `~` and links are resolved, a wrapped `sh -c`, a plan-named exception). A hook fails open on a timeout or a mistyped path, so nothing here relies on the guard alone, and every seat contract still states every item. The after-check is [the diff check](../diffcheck/README.md), which the pre-push hook runs.

| File | What it is |
|---|---|
| [`policy.py`](policy.py) | The rules as data: seats and their write zones, controls, credentials, records, snapshot flags, the machine-local lists. One copy, read by everything below and by [the diff check](../diffcheck/README.md) |
| [`guard.py`](guard.py) | The PreToolUse hook, one script for both vendors. Exit 2 with a reason refuses; every decision is appended to the pass's guard log |
| [`shellparse.py`](shellparse.py) | Splits a command line into the simple commands the guard judges: `sh -c`, `$(…)`, `env`, `cd`, redirects, heredocs |
| [`gitcheck.py`](gitcheck.py), [`git/`](git/) | pre-commit, commit-msg and pre-push for a build worktree |
| [`seat.py`](seat.py) | The coordinator's tool: writes a pass's seat context, its Claude settings or Codex pass profile, the Codex seat home, a worktree's git hooks; files the release gate's checks with their invocations; launches a pass under its caps, a release gate only on its evidence; freezes a diff; runs the model check and the preflight |
| [`tests/`](tests/) | The seeded cases (must refuse, must pass) beside the hooks, the Codex sandbox matrix, and `live.py` |

## How a pass is walled

1. **Open** installs the worktree's git hooks: `seat.py worktree <worktree> --engagement <eng>`. It sets `core.hooksPath` for that worktree only (`extensions.worktreeConfig`), so Sean's own checkout never runs them.
2. **Before each pass** the coordinator writes the seat context, copying every plan-named exception from the plan gate's frozen "Exceptions on the record" table and nowhere else: `seat.py context --seat <seat> --worktree <wt> --engagement <eng> --pass NN --branch <branch> [--test-path P] [--ops-path P] [--grant-read F] [--grant-control F] [--host H] [--cap-minutes N] [--cap-tool-calls N] [--cap-budget-usd N] [--effort xhigh] [--escalation <record>] [--verify <artifact> | --anchor <artifact> [--fallback <issue>]] [--candidate <commit>]`. It lands in `<eng>/trace/logs/pass-NN.context.json`, written once, with the pass's caps: the seat's defaults (the Builder 60 minutes and 200 tool calls, the Codex gates 20 and 80, the Claude seats and the security pass 30 minutes and $15) unless the Open changed them with a stated reason. It holds no employer paths. A Codex pass runs at effort `high`; **the Builder's escalated repair** takes the one step above it, `--effort xhigh`, only with `--escalation` naming the record that calls it: the gate findings whose FAIL sent the redraft up (`audits/<gate>[-rN].md`, its verdict a FAIL), or the ledger entry (`dNN-<slug>.md`) that names `xhigh` for another trigger. Any other effort (never `ultra` or `max`), a gate or a record outside the engagement folder stops at `context`; the record's hash goes in the context, `launch` refuses if it has changed since, and the launch record carries the effort and the record (SWCB #135).

   **A pass on the other vendor** (SWCB #126). The context also fixes the vendor the pass runs on, read from a record, never chosen, and the launch record carries it as `vendor_basis`. The record's hash goes in the context and `launch` refuses if it has changed since. Four cases, and anything else runs on its seat's own vendor:
   - **A verification pass** (round two of an audit) names the repaired artifact: `--verify artifacts/<file>`. The launcher reads its header's `model:` line, takes the runtime after the last arrow as the repair's writer, and runs the pass on the other vendor, read-only (craftwork § Model delegation: the checker changes vendor, not the repairer). This is how the Verifier's verification pass after a Planner repair, and Release's after a Verifier repair, reach Codex. Neither changes a test, so the Verifier's brake does not apply.
   - **A Claude seat's redraft one tier up** names its record with `--escalation`, as the Builder's does. The ladder is Opus 5.5 → Codex high → Codex xhigh → stop and ask Sean, so the Planner's or Release's redraft runs on Codex, `gpt-6.1-sol` at `high`. The step after that, `--effort xhigh`, takes a ledger entry that names it; a gate FAIL buys one step. The Verifier never escalates onto Codex: `--escalation` on the Verifier stops at `context`.
   - **Every gate names its anchor**: `--anchor artifacts/<file>` (the build plan for the plan gate, the release plan for the release gate, the change note for the security pass). The gate runs on the vendor that did not last write it, read from the same `model:` line. A plan or release gate whose anchor was last written on Codex runs on Opus 5.5, read-only; a security pass whose anchor was last written on Claude runs on Codex at the gate default. A gate without `--anchor`, or an anchor whose writer can't be read, stops at `context`. Anchors and repaired artifacts sit in `artifacts/` or `inherited/`.
   - **`--fallback <issue link>`** keeps a gate or verification pass on the writer's vendor when the planned one is unavailable, naming the re-run ticket the red-team protocol files (`fallback: same-vendor`).

   A moved pass takes the caps of the vendor and kind of pass it becomes: on Claude 30 minutes and $15, a read-only pass on Codex 20 minutes and 80 tool calls, a redraft on Codex 60 minutes and 200 tool calls (Sean, SWCB #126). Every pass on Codex pins `gpt-6.1-sol` (the Builder's model and the gate default) at `high` unless the record calls `xhigh`; every pass on Claude pins `claude-opus-5-5`. The guard asks the vendor, not the seat's name, whether a pass may write the engagement folder: a pass on Codex never does, since its one output is filed by `-o`.
3. **The wall files** hold the machine's employer paths, so they are written once to `~/.config/devcraft/passes/<engagement>/` (`$DEVCRAFT_PASSES` for tests), outside every repo; the pass record keeps their path and hash, never their content. **A pass on Claude** (a Claude seat, the security pass, or a pass moved there): `seat.py claude-settings <context>` writes `pass-NN.settings.json`: sandbox on and failing closed, no escape hatch, network limited to the plan's hosts, `denyRead` and `Read` denies for credentials, Sean's own `~/.codex/` (step 7), employer paths and (for all but the Verifier) `held-out/`, `Edit` denies for controls, records, the shared references and everything outside the seat's zone as the worktree stands, git writes only to the build branch's own refs, and the guard on `PreToolUse` and `SessionStart`. The security pass is a gate on Opus 5.5, so it runs read-only: the worktree and the engagement folder are in its `Edit` denies, and its one write tool is `Write`, which reaches only its scratch folder (step 6); so does any gate or verification pass moved to Claude. **A pass on Codex** (the Builder, the plan and release gates, or a pass moved there): `seat.py codex-pass <context>` writes `pass-NN.codex-layer.toml` and links the seat home's `<eng>-pass-NN.config.toml` to it, since Codex reads a profile only from its home: the Builder's extends `:workspace` with test paths, Release's ops paths and every control (present or not) read-only, a test or ops path meaning every match of a floor pattern at any depth as the worktree stands when the layer is written, plus each glob-free pattern's top-level path even when absent (a match created later elsewhere, such as a new nested `tests/`, is the guard's, the commit hook's and the diff check's); Release's escalated redraft extends `:workspace` with everything but its ops paths read-only, test paths and controls included; every other pass on Codex (a gate, a verification pass, the Planner's redraft, whose one output is its final message) extends `:read-only`; all deny credentials, Sean's own `~/.codex/` but Codex's install in it (step 7), employer paths and, for every seat but the Verifier, `held-out/`, keep the engagement folder read-only and the network off, and mark the worktree untrusted so a repo's own `.codex/` config never loads.
4. **Launch** with `seat.py launch <context> --prompt-file <f> [--output artifacts/<file>] --run`: a scrubbed environment (no tokens, stdin closed), `--setting-sources ""` for Claude, `-p <profile>` and no `--sandbox` for Codex. The forms are in [the bench README](../bench/README.md#launch-forms). A Codex pass, and a read-only Claude pass, names its artifact with `--output` (in `artifacts/` or `audits/`, written once): Codex writes its final message there with `-o`, and the launcher files a read-only Claude pass's final answer there. The launcher watches the live log (`trace/logs/pass-NN.jsonl`, stderr beside it) and **kills the pass's whole process group at 100% of a cap** (wall clock, or tool calls counted from the log), because Codex has no budget, turn or time flag and macOS has no `timeout`; Claude stops itself at `--max-budget-usd`. Either stop is filed `Blocked: budget` with what the pass left on disk (exit 2). After a Codex pass it saves the session files as `pass-NN.rollouts/` and reads them as rung-0 line 11 does: a pass that started a helper agent has its output moved aside to `pass-NN.discarded.md` and exits 3, to be re-run once as a new pass (a second spawn stops Blocked, #123). Everything the record's completion fields need lands in `pass-NN.launch.json`: times, tool calls, the stop, the wall file's path and hash, the output's hash, the raw usage and its meter source, the session stamps. A release gate launches only on its evidence at the candidate (step 8); without it the launch stops with exit 4.
5. **The frozen diff.** After a pass that touched the target repo, `seat.py freeze-diff <context> --base <base> [--point HEAD]` saves `git diff <base>..<point>` (binary-safe, no personal git settings) as `<eng>/artifacts/pass-NN.diff.patch`, written once, and prints its hash and both commits for the pass record. The patch outlives the worktree.
6. **The scratch folder** (SWCB #148). dc-eng-003's read-only passes could not run a Python probe or copy the tree to run the suite on: the guard refused `git archive` as a git write and every write outside the worktree, and Claude's headless session refused every command that would have asked for approval. So `context` gives every pass one empty folder, `~/.cache/devcraft/scratch/<engagement>/pass-NN/` (`$DEVCRAFT_SCRATCH_ROOT` for tests), mode `0700`, refusing one inside any repo or one already holding files, and records it in the context. It is the one place a read-only pass writes, and every pass may write there: on Claude it is in the sandbox's `allowWrite` and an `--add-dir`, and a read-only pass gets `Write` (never `Edit`) for it; on Codex it is a `"write"` entry in the pass layer, `:read-only` included; the guard allows any write under it. No pass reads another pass's scratch folder, since a Verifier's may hold copies of `held-out/`: the folders that exist when a wall is written are in its read denies on both vendors, and the guard refuses any of them. The launch sets `TMPDIR` and `DEVCRAFT_SCRATCH` to it, so `mktemp` and Python's `tempfile` land there and a seat finds it with `echo $DEVCRAFT_SCRATCH`, then writes the path out in full: the guard never expands the variable, which the command itself could reassign; the launch record names it. `git archive` counts as a read for every seat (never `--remote` or `--exec`; its `-o` must land where the seat may write), and `tar`'s extract folder and created file are judged as writes. The forms that work with nobody to answer an approval prompt are in [the seat preamble](../templates/seat-preamble.md) and [the gate schedule](../templates/gate-schedule.md): one plain command per call, every path written out, a probe run as `/usr/bin/python3 -B <file>`. The diff check still runs only outside every sandbox, because it reads the machine-local name list no pass may read. Nothing in scratch is filed or cleaned up by the launcher.
7. **Sean's own Codex home** (SWCB #149). dc-eng-003's pass 18, a Builder audit on Codex, read `~/.codex/skills/.system/review-agent/SKILL.md` in Sean's real Codex home, because the Builder's toolbelt named that path. Codex itself never loads it: run under the seat home, it finds skills in two places only, the seat home's own `skills/.system/`, which Codex installs in every home, and `~/.agents/skills/` (read from Codex's rendered prompt, `codex debug prompt-input`, no model call). So the toolbelt now names the seat home's copies, and `codex-home` copies the plugin skills the toolbelt names (superpowers' `executing-plans` and `verification-before-completion`) from the newest cached version into `<seat home>/toolbelt/`. Every pass is denied `~/.codex/`, on both vendors and in the guard, with one opening: Codex's install, `~/.codex/packages/`, stays readable in a Codex pass's layer and to the guard, because Codex's sandbox re-runs its own binary from there and denying it stops Codex before any command runs. A pass on Claude never runs Codex, so its sandbox denies the whole folder. `codex-home` refuses a seat home inside `~/.codex/`. `seat.py check` reads the skill roots each time and reports a gap if one sits in `~/.codex/` or the table cannot be read, and a gap for a missing toolbelt copy.
8. **The release gate's evidence** (SWCB #150). dc-eng-002's release gate carried two findings on the coordinator's own evidence (lint suppressions never frozen; no drill at the candidate, a dependency scan scoped wrong, no invocation recorded), and dc-eng-003's failed its first round on nothing but the diff check's missing execution record. So a release gate's context names its candidate, `--candidate <commit>`, resolved to the full hash, and the coordinator files the secret scan and the dependency check with `seat.py record <gate context> --check secrets|deps|drill -- <tool by full path> <args>`: it refuses unless the worktree is at the candidate, runs the tool there outside any sandbox, and writes `evidence/<check>-<candidate>.txt` (a re-run `-2`, `-3`, never overwritten) with the cwd, the command, the tool's path and `--version`, its interpreter, the worktree's `HEAD` and status and the exit code above the output. `seat.py launch` then refuses a release gate with **exit 4**, listing each gap, unless `evidence/` holds at the candidate: the drill (`drill-<candidate>.txt`, or the file the release plan's **Commands and output** line names, at the hash it gives, naming the full candidate hash); a secret scan and a dependency check filed by `record`; and the newest diff-check report, its own invocation complete (SWCB #146), at the candidate, not in fixture mode, and exiting 0, so every hit is matched to a frozen exception or a dated yes. A scan's own findings, leaks or vulnerabilities, are the gate's to judge, never a refusal. The launch record lists each evidence file with its hash. A release-gate context written before this has no candidate and does not launch; write the gate a new one.

`seat.py probe` is the model check at Route: one tiny call per pinned id (`claude-opus-5-5` on `claude -p`, and `gpt-6.1-sol` on `codex exec`, effort `high`, which is both the Builder's model and, since 2026-10-12, the gate default), printed as the Route entry's lines. The match is read from the log's model stamp, never from the answer: on 2026-10-12 GPT-5.6 Sol answered "gpt-6.1-sol" and GPT-6.1 Sol said it did not know, while both logs stamped the right model. Exit 1 on any mismatch, which goes to Sean before any seat runs.

`seat.py check` is the preflight: both machine-local lists present, the scanners at their full paths, the Codex seat home signed in and its guard trusted at its current hash, its toolbelt copies present, and no skill root Codex finds under it inside Sean's own `~/.codex/`. Run it before every engagement; a gap stops the engagement at Open.

## The machine-local lists

Two files outside every repo, in `~/.config/devcraft/` (override with `$DEVCRAFT_LOCAL` for tests), one entry per line, `#` for comments: **`employer-paths`**, folders denied at the OS level (never-do 2), and **`names`**, the employer, client and startup names the git hooks refuse (never-do 11). Sean writes both by hand on each Mac. Neither is ever tracked, quoted or shown to a seat: the folder is in every pass's read deny, and a hit is reported by file and line, never by the name. A missing or empty list refuses every call: the wall fails closed. That includes a `git commit` run inside a seat's sandbox, so seats never commit: the coordinator commits a seat's staged paths under the seat's context (`DEVCRAFT_CONTEXT` and `DEVCRAFT_SEAT` set), where the hook can read the list and still applies the seat's zone ([the bench](../bench/README.md), SWCB #133).

## What the guard cannot see

A script the seat writes and then runs (`python3 x.py`) does whatever the sandbox lets it; that is why the sandbox is the wall. On Claude, file tools and hooks run outside the sandbox, so `Read` and `Edit` denies cover the file tools. A new file a Verifier or Release creates outside its zone after the settings were written is the guard's alone. Codex's sub-agent tools cannot be switched off: a spawn is caught from the pass log (`collab_tool_call`), never prevented.

## Tests

```bash
cd ~/Code-Brain/studios && uv run --no-project --with pytest python -m pytest devcraft/hooks/tests -q
```

The seeded cases run every call through the guard in both vendors' payload shapes, under `/usr/bin/python3` and the current Python; the git hooks run through real commits; the Codex profiles run through `codex sandbox`, the real Seatbelt policy, with no model call; the launcher's caps, kill switch, helper catch, output filing, release-gate evidence check and probe run against a fake `codex` and `claude` put first on `PATH`. `python3 devcraft/hooks/tests/live.py` then sends one real seat session per vendor into a fresh worktree and reads the guard log and the worktree, never the seat's own account, to confirm each vendor held, and launches one real Builder pass through `seat.py launch` capped at two tool calls, which must be killed at the second, then two cross-vendor launches: the Verifier's verification pass on Codex and a plan gate moved to Opus 5.5 (SWCB #126), then a read-only security pass on Claude and a read-only release gate on Codex, each writing and running a probe, copying the tree with `git archive` and failing to write the worktree, the Claude one with nothing in scratch held for approval (SWCB #148). Before the sessions it reads the skill roots Codex finds under the seat home, and both first sessions try Sean's own `~/.codex/`, which must be refused, the Codex one then reading the seat home's copy of the same skill (SWCB #149).
