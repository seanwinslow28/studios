# The launcher

Motioncraft's launcher runs one seat pass on either vendor, under its caps and inside its write fence, and leaves the logs the pass record is built from. Built on the Motioncraft build map's **Build the slim Motioncraft launcher** ticket (2026-10-19), as ruled on Master skill design (SWCB #192, item 10): a slim copy of Devcraft's [`seat.py`](../../devcraft/hooks/seat.py) with only what Motioncraft needs, Devcraft untouched. The master skill's Run phase launches every pass through it; the per-seat launch forms, the plugin allowlist and the image doorway were finished on the **Plugin allowlist and launch form for seat runs** ticket (2026-10-19).

Kept from Devcraft: the per-pass caps and the kill at 100%, the model probe, the isolated launch on both vendors, the vendor read from a record (a gate's anchor, a verification pass's repair, a redraft's escalation), helper-agent detection, the scratch folder, and the logs. Added: the write fence and the machine check. Left with Devcraft: the guard hook, the git hooks, worktrees, the frozen diff and the release gate's evidence, all built around code.

| Command | What it does |
|---|---|
| `seat.py context --seat S --engagement E --pass NN [...]` | Writes `<E>/trace/logs/pass-NN.context.json`, once: the seat, the vendor and the record that says so, the caps, the effort, the machine, the media project read from the brief's `media:` line, the scratch folder, and the fence |
| `seat.py claude-settings <context>` | A pass on Claude: its settings file, sandbox on and failing closed |
| `seat.py codex-home` | The Codex seat home, `~/.codex-motioncraft`: plugins, apps, memories, multi-agent and image generation off, a read-only floor |
| `seat.py codex-pass <context>` | A pass on Codex: its permission layer, linked into the seat home as `<eng>-pass-NN.config.toml` |
| `seat.py launch <context> --prompt-file F --output A --run` | Runs the pass, its record named by `--output`, and writes `pass-NN.jsonl`, `pass-NN.stderr.log`, `pass-NN.launch.json` and, on Codex, `pass-NN.rollouts/` into `trace/logs/` |
| `seat.py toolbelt` | Copies each seat's skills from [`bench/toolbelts.toml`](../bench/toolbelts.toml) into `~/.local/share/motioncraft/toolbelt/<seat>/`: a Claude plugin of copies with a manifest of each source's hash. A missing skill is a gap |
| `seat.py seat-probe [--seat S]... [--read-only] [--logs DIR]` | One probe pass per seat (all four by default; gates by name) on its own launch form, judged from what the vendor reports it loaded: exit 1 on anything beyond the toolbelt, or on a pass that cannot open the private library. `--read-only` probes each seat in its audit form. Logs go to `--logs` with the employer folders redacted |
| `image.py --context C --out F --prompt-file P [--ref R]...` | The image doorway: run by a Director's or Art's pass, never by the coordinator ([below](#the-image-doorway)) |
| `sound.py --context C --cue FXn\|MUn --out F` | The sound doorway: run by a Finishing pass, never by the coordinator; `--status` lists the approved cues, the takes and the spend ([below](#the-sound-doorway)) |
| `higgsfield.py take --context C --entry IMn\|VIn --out F`, `higgsfield.py status --context C` | The Higgsfield doorway: run by the launcher for an Art or Animator pass's `apps.py ask higgsfield`, never by a seat; `status` lists the approved entries, the takes and the credits ([below](#the-higgsfield-doorway)) |
| `filing.py <engagement> [--pass pass-NN]... [--check]` | Filing a pass's logs: images and sound stripped, the employer folders replaced; run by `launch` at the end of every pass ([below](#filing-a-passs-logs)) |
| `freeze.py sweep <project> [--json]`, `freeze.py lock <project> [--version STAGE/NAME]...` | Every version folder in a media project read by its mode bits: the sweep the Close checklist runs, and the lock by hand for an approved copy or a version from before the launcher locked, only where its checksums verify ([below](#freezing-versions)). `launch` locks each whole version a pass made the same way |
| `apps.py ask blender\|resolve\|krita --script F [...]`, `apps.py ask higgsfield --entry E --out F` | The application doorway: a pass asks from its shell, and the launcher runs Blender, a Resolve script or Krita for it ([below](#the-application-doorway)), or the Higgsfield doorway ([below](#the-higgsfield-doorway)). `apps.py lock <context> blender\|resolve\|krita` prints the lock a call would run under |
| `seat.py probe [--logs DIR]` | The alias probe at Route: one tiny call per pinned id, printed as the Route entry's lines |
| `seat.py check` | This machine's preflight for the launcher: both CLIs, the `media` folder mapped, the employer-path list, the seat home set up and signed in, every toolbelt copy built and matching its source, the applications' paths |

The coordinator runs these; no seat does. Without `--run`, `launch` prints the command line, the environment's names, the caps and the fence, and starts nothing.

## The context

Everything a pass runs under is fixed in its context, written once before the pass, and the launch reads only that.

- **Seats.** The four seats (`visual-story-director`, `art-pose-designer`, `animator`, `finishing-sound-designer`) and the four gates (`story-gate`, `appearance-gate`, `motion-gate`, `self-check`, the held checks among the motion gate's passes).
- **Vendor, read from a record, never chosen.** A gate names its anchor with `--anchor artifacts/<file>` and runs on the vendor that did not last write it, read from the anchor's `model:` line. A verification pass names the repair with `--verify` and runs read-only on the other vendor. A redraft one tier up names its record with `--escalation` (a gate FAIL in `audits/`, or a `dNN-` ledger entry that names the step): a Claude seat's redraft runs on Codex at `high`; the Animator's takes `--effort xhigh`, the one step its ladder has before Sean. `--fallback <issue>` keeps a gate on the writer's vendor when the planned one is unavailable. The record's hash goes in the context, and a record changed since stops the launch.
- **Caps** ([master skill § Pass budget and launcher caps](../../.claude/skills/motioncraft/SKILL.md#pass-budget-and-launcher-caps)): Claude seats and the motion gate 30 minutes and `--max-budget-usd 15`; the Animator 60 minutes and 200 tool calls; the Codex gates, the self-check gate among them, 20 minutes and 80 tool calls. A pass moved to the other vendor takes that vendor's caps for its kind: on Claude 30 minutes and $15, a read-only pass on Codex 20 and 80, a redraft on Codex 60 and 200. `--cap-*` changes them, with the why in the brief.
- **The machine.** The context records the machine it was written on, and `launch` refuses on any other: one machine per job, and a job moved to the other machine writes its next context there.
- **Network.** Off on Codex. On Claude, only the hosts `--host` names.

## The write fence

Read from the brief's `media:` line and the machine's `folders.local` ([the trace kit's named folders](../../craftwork/trace/README.md)), so it works the same on the laptop and the Mini. A brief without one, or a `media` name this machine has not set up, stops at `context`: no film job opens without its media folder.

| Pass | May write | Frozen inside it |
|---|---|---|
| A drafting seat, or its redraft | its own stage folder in the media project (`story/`, `appearance/`, `motion/`, `finish/`), for new version folders; on Claude, the engagement's `artifacts/`, for new files | every version folder and every artifact already there when the context was written |
| A gate, an audit (`--read-only`), a verification pass | nothing | |
| Every pass | its scratch folder, `~/.cache/motioncraft/scratch/<eng>/pass-NN/`, outside every repo, new and empty, and its `TMPDIR` | |

A pass on Codex never writes the engagement folder: its one output, the scene record or the gate's findings, is its final message, which `-o` files. A read-only pass on Claude gets `Write` for its scratch folder only, and the launcher files its final message with `--output`. A drafting pass on Claude writes its own record, at the path `--output` names. Nothing outside these folders is writable, so a seat never touches another seat's stage, `inputs/`, `approved/`, the brief, the ledger entries, the trace, or the studio's own files.

Every pass is denied reading credentials, Sean's own `~/.codex/` (Codex's install inside it stays readable on Codex, which re-runs it), the engagement's other scratch folders, and the folders on the machine's employer-path list (`~/.config/devcraft/employer-paths`, one list per machine, written by hand and never tracked). The wall files hold those paths, so they live in `~/.config/motioncraft/passes/<eng>/`, outside every repo, written once.

**What it holds by.** On Codex, the permission layer, enforced by Codex's own sandbox: the tests run each Codex layer through `codex sandbox`, the real policy, with no model call. On Claude, the settings file and the working folders. Commands run in the sandbox, whose write list is the fence. The file tools run outside the sandbox and write only inside a pass's working folders, so a pass is given only the folders the fence lets it write (`--add-dir`; none for a read-only pass, whose working folder is its scratch), `Edit` denies freeze what is already in them, and `Read` rules let it read the engagement, the media project, `motioncraft/`, `craftwork/` and the studios `AGENTS.md` from outside them. A live Director pass on 2026-10-19 confirmed both halves: it wrote a new version folder and a new artifact; its shell and its Write tool were refused on a saved version, another stage, the brief, a new file or folder at the engagement's top level and the media project's, and the employer folder. A file created after the context was written is outside the frozen list.

## The launch

- **Isolated.** A scrubbed environment (no tokens, stdin closed). Claude: `--setting-sources ""`, `--strict-mcp-config`, the scratch folder as its working folder, a limited `--tools` list with no tool that starts a helper, the studios `AGENTS.md` by flag, the seat's toolbelt copy as its one plugin, and no hooks. Codex: from the seat home with `-p <eng>-pass-NN`, `--model gpt-6.1-sol` and the effort spelled out, never the config default and never `ultra`, web search off, the media project as its working folder, marked untrusted. Its prompt opens with the studios `AGENTS.md` and the toolbelt's skills by path, since neither is found from the media project.
- **The toolbelt.** The context fixes the seat's toolbelt copy by its manifest's hash, and a copy changed since stops the launch. A drafting pass whose allowlist line names `tools` (Devcraft's modules in [`../tools/`](../tools/README.md)) has each fixed by its file's hash and named by path in its prompt, on either vendor; a tool changed since stops the launch, and a listed tool missing is a gap in `seat.py check` (SWCB #255). Every pass is denied every other skill folder. Every pass's environment carries the allowlist's `[env]`: Blender's folder on `PATH`, Resolve's scripting variables.
- **Held commands.** Claude Code holds an `ffmpeg` or `ffprobe` call with a `name=value` option for an approval no one gives; a Claude pass without a doorway gets an allow rule for both, still sandboxed. A pass with the image or sound doorway (the Director's, Art's and Finishing's drafting passes) does not, since the same rule would let them out of the sandbox; its prompt says to pass filters from a file (`-/vf <file>`, `-/af <file>`; a loudness check is a file holding `ebur128=peak=true`, tested on ffmpeg 8.0.1). Sean chose this over a separate sound pass on the sound doorway ticket (2026-10-19).
- **Caps.** The launcher watches the live log and kills the pass's whole process group at 100% of a cap (wall clock, or tool calls counted from the log); Claude stops itself at its budget. Either stop is filed `Blocked: budget` with what the pass left on disk, exit 2. The prompt states the caps, so the seat stops itself at 90%.
- **Helper agents.** On Codex the session files are saved to `pass-NN.rollouts/` and read as rung-0 line 11 reads them; on Claude the log is read for a `Task` or `Agent` call or a helper's message. Either way the output is moved aside to `pass-NN.discarded.md` and the launcher exits 3: re-run once as a new pass, and a second spawn stops Blocked.
- **Versions** (SWCB #249). mc-eng-001's tasks asked every seat for a version's pointer and checksums and never for its `manifest.md`, and nobody noticed until Finishing's TC5 failed on it at the end. So every drafting pass's prompt, on either vendor, carries one note after the coordinator's task: every version it saves is a new folder in its stage holding `pointer.txt`, `manifest.md` (the source contract's § 3) and `checksums.sha256`, by those names. After the pass, every folder in its stage that the context did not freeze is read as a version this pass made and listed in the record's `versions` with any of the three it lacks (a name in any case counts, so the October versions' `POINTER.txt` does). One that lacks any is refused: `version refused` in the outcome, exit 5 (a budget stop or a helper keeps its own exit), and the version goes back to its seat, never on to the next one or a gate. A gate, an audit and a verification pass save no version and are not checked. **Each whole version is then frozen** ([below](#freezing-versions), SWCB #258).
- **The private library** (SWCB #250). The seat, lane and preamble text in a task points into the corpus by links written from the lane file's folder (`../corpus/...`), which mean nothing from a pass's working folder. In mc-eng-001 one read-only audit guessed a wrong folder and gave up, four never tried, and one found it, though every pass's settings let it read the corpus. So every pass's prompt, on either vendor, carries one note naming the corpus by its full path on this machine and saying a `../corpus/<path>` pointer means `<that folder>/<path>`; on a machine without the corpus, the note says so and the pass's grounding is `manifest-only`.
- **The pass's record** (SWCB #261). mc-eng-001's tasks were written by hand and nothing checked them, so a required output could drop out unseen (every version missed its manifest until stage 4, d14). Every launch now names the pass's record with `--output`, checked against its kind before anything runs: a drafting pass's is a `.md` in `artifacts/`; an audit's, a verification pass's and a gate's a `.md` in `audits/`; a gate's by its own name (`story-gate`, `appearance-gate`, `motion-gate` or `revision-check`, `self-check-gate`, each with an optional part and round). The prompt, on either vendor, carries a note naming the record and the template it follows: the shared header and the seat's template for a draft, the check record for an audit, the gate findings (and the held checks' form for `revision-check`) for a gate. When the pass ends without that file the outcome says `record missing: <path>`, exit 6 (a budget stop, a vendor failure or a refused version keeps its own exit); a helper catch has already moved it aside. The launcher writes the final message there only for a Codex or read-only pass, never over a drafting Claude pass's own record.
- **The record.** `pass-NN.launch.json` holds what the pass record's completion fields need: times, tool calls, the stop, the machine, the media project, the fence, the wall file's path and hash, the outputs and their hashes, the raw usage and its meter source, and the runtime stamps from the log. After a Claude pass the launcher removes any `.claude` folder the pass left inside its fence, its own new version folders included, if it holds only empty folders or Claude Code's `.cc-writes`, and names the rest; both lists go in `claude_dirs`.

## The image doorway

`image.py` is the Director's and Art's one way to the Codex image path. Their pass settings let exactly `image.py --context <this pass's context>` out of the Claude sandbox, when the pass asks for it with `dangerouslyDisableSandbox`; any other command that asks is held for an approval no one gives, and a chained or substituted second command is held too (live, 2026-10-19). Inside the sandbox it could not work: Codex could neither read its seat home's sign-in, which every pass is denied, nor start its own sandbox. So the doorway holds the fence for the call:

- the context must sit in its engagement's `trace/logs/`, where no seat writes, and say the pass may use the image path (a drafting Director or Art pass on Claude);
- the image lands as a new `.png` in a version folder the pass made in its own stage, never a saved one;
- the prompt comes from the pass's scratch folder or that version folder, and every `--ref` is an image in the media project, at most five;
- Codex runs from the seat home with image generation on and its shell off (`shell_tool`, `unified_exec`) for this call only, `--model gpt-6.1-sol` at `high`, the prompt on standard input, since the call runs outside the seat's sandbox and a shell could read what the seat cannot; a run whose log shows a command, a file change, a connector call or a helper files nothing;
- the image Codex saved under `generated_images/<thread>/` is filed whatever the exit code, with `<name>.image.json` beside it (the prompt, the references and their hashes, the run, the label "generated"), both created relative to the version folder held open since the check, never through a link and never over a file already there; the call is logged to `trace/logs/pass-NN.images.jsonl`.

## The sound doorway

`sound.py` is Finishing's one way to generated sound: sound effects from ElevenLabs (`eleven_text_to_sound_v2`, MP3 at 192 kb/s, the best the Creator plan gives) and music from Lyria on the Gemini API (`lyria-3-clip-preview`, a 30-second clip at $0.04, or `lyria-3.5`, a song at $0.08), under Sean's intended-use approval (mc-setup-004). Built on the map's **Finishing's sound doorway** ticket (2026-10-19), on the image doorway's pattern: the pass's settings let exactly `sound.py --context <this pass's context>` out of the Claude sandbox; inside it the pass has no network and cannot read the keys file (`~/.config/audio-keys/`, on every pass's credential wall, Codex's included). The doorway holds the terms for the call:

- the context must sit in its engagement's `trace/logs/` and say the pass may use the sound path (a drafting Finishing pass on Claude: `sound = true` in [`bench/toolbelts.toml`](../bench/toolbelts.toml), which only Finishing may carry);
- **the approved cue list.** Finishing's sound plan writes the cues to generate as `cues.json` in a version folder in `finish/` (below). Sean approves the list in one decision; as for any approval, the exact folder is copied to the media project's `approved/<version-id>/` and made read-only, and his approvals entry names it (`version_path`, absolute or `media:…`, and `version_sha256`, the trace kit's folder hash). The doorway reads the newest such entry with `decision: approved` for the job, and refuses if the copy no longer matches its hash;
- **a cue by its id, and nothing else.** The tool, the model, the prompt and the settings are the list's, sent as they stand; only the text prompt goes out, never a file. A reworded cue is a new list for Sean, never a take;
- **three takes a cue**, counted across the whole job (every pass's `*.sounds.jsonl`), per cue and its exact approved wording. A call that fails makes no take;
- **two caps from the brief**, both required: `spend_cap_usd` for Lyria, which bills per call (price table in `sound.py`, from the pricing page read for SWCB #215), and `sound_credits_cap` for ElevenLabs, whose prepaid plan can buy nothing more, so its credits are counted instead of dollars (Sean's ruling, 2026-10-19). A take that would cross either is refused before any call, and that is a checkpoint for Sean. ElevenLabs credits are read from the account before each take and again until its count moves, up to 90 seconds, since the count lags a take by some seconds (live, 2026-10-19); a count that never moves is charged the estimate, the larger of 200 or 40 a second, which is what ElevenLabs's pages give, though the live take cost 15. One lock makes the job's takes one at a time;
- the take lands as a new file in a version folder the pass made in its own `finish/` stage, `.mp3` (a WAV answer is filed as `.wav`), with `<name>.sound.json` beside it: the approved cue, the approval, the take number, the service, model and request (no key), the cost, the hash, any text Lyria returned, and the label "generated". Both are created relative to the version folder held open since the check, never through a link and never over a file already there. Audio that came back but could not be filed is kept in the pass's scratch folder and counts as a take. Every call, refusals included, is a line in `trace/logs/pass-NN.sounds.jsonl`.

Lyria can answer with text beside the audio (lyrics or structure). The doorway records it and tells the pass to listen for sung words before a take goes in the cut, since words in the film are Sean's (rule 8). The approved prompt should ask for an instrumental.

The cue list, `cues.json`:

```json
{"cues": [
  {"id": "FX1", "moment": "SP2", "tool": "effect", "prompt": "<text>", "duration_s": 1.5, "loop": false, "prompt_influence": 0.3},
  {"id": "MU1", "moment": "SP1", "tool": "music", "model": "lyria-3-clip-preview", "prompt": "<text>"}
]}
```

`FX<n>` is a sound effect and `MU<n>` music; `moment` is the sound plan's `SP<n>`. An effect may set `duration_s` (0.5 to 30, or left out for the service to choose), `loop` and `prompt_influence` (0 to 1); music sets `model`. A list naming anything else is refused whole.

## The Higgsfield doorway

`higgsfield.py` is how Art makes Higgsfield images and the Animator Higgsfield video, and no other seat calls Higgsfield (Sean's pick at mc-eng-002's Open, 2026-10-24, "Doorway ticket (Recommended)": SWCB #271). It holds the sound doorway's terms, in credits. It is reached another way, though: the Animator runs on Codex, and Codex's sandbox has no rule that lets one command out the way the image and sound doorways' Claude passes are let out. So a pass asks the launcher, through the application doorway's request folder, `python3 -B apps.py ask higgsfield --entry IM1 --out <file>` (or `--status`), and the launcher runs `higgsfield.py take` for it outside every lock, since the call needs the network and the sign-in. Inside its sandbox the pass has neither: `~/.config/higgsfield/` is on every pass's credential wall, and no Claude pass may run `higgsfield` at all. The call's log is the application doorway's (`pass-NN.apps/<id>.log`), and its line goes in `pass-NN.apps.jsonl` too. The doorway holds the terms:

- the context must sit in its engagement's `trace/logs/` and say the pass may use Higgsfield, and for which kind: `higgsfield = "image"` on Art's line in [`bench/toolbelts.toml`](../bench/toolbelts.toml) and `"video"` on the Animator's, which only those two may carry; a drafting pass, on either vendor;
- **Sean's intended-use approval first, for this job.** The intended use is per engagement: a setup record in the ledger's `setup/` whose header says `tool: higgsfield` and names the brief's `id` in `engagements: [mc-eng-NNN, ...]` records Higgsfield's data-use and training settings and the use Sean approved for that job, and its `intended_use_approved:` carries the date of his approval (never-do 6). `mc-setup-023` covers `mc-eng-002`. Another job's record never covers this one. A record that another approved record for the job names in its `supersedes:` (one id, or `[a, b]`) is skipped: `mc-setup-027` supersedes `mc-setup-025` for `mc-eng-003`. With no record standing for the job, with two, or with `pending`, every call is refused;
- **the approved list.** The seat writes the entries it needs as `higgsfield.json` in a version folder of its stage. Sean approves the list in one decision; as for any approval, the exact folder is copied to the media project's `approved/<version-id>/` and made read-only, and his approvals entry names it (`version_path`, `version_sha256`). The doorway reads the newest such list of the pass's kind, and refuses if the copy no longer matches its hash. A list is all images (`IM<n>`) or all video (`VI<n>`), names the test it serves and that test's ceiling, and nothing else;
- **an entry by its id, and nothing else.** The model, the prompt and the settings are the list's, sent as they stand, each setting checked at the call against what Higgsfield says the model takes (`higgsfield model get`), and each value a word, a ratio or a size. A reworded entry is a new list for Sean, never a take;
- **no upload, unless the job's setup record allows approved media.** The `higgsfield` command line uploads any local file a media flag names, so none of a model's media settings goes out but `start_image`, `end_image` and `image_references`, and each names an earlier take of this doorway's own in this job, by its Higgsfield job id (`job:<id>`), already on Higgsfield's side. Only where the job's setup record says `uploads: approved-media` (mc-setup-027, for mc-eng-003) may it also name an image in one of this job's approved copies, by its path from the media project: `approved/<version-id>/<file>`, no part starting with a dot. At the take, before anything is sent, each such file must exist, be a regular file reached through no link, sit in a copy named by an approvals entry with decision approved whose `version_sha256` still matches the folder, be listed in that copy's `checksums.sha256`, and match its listed sha256 byte for byte; it must be a png, jpg or webp. The bytes checked are copied to a private folder and uploaded from there (`higgsfield upload create`), once each, after the model is known to take the field and before the take is priced, and the take goes with the upload's id. Higgsfield's uploads fail now and then with "Failed to upload media bytes." on a file that goes through on the next call (mc-eng-003's pass-34 and pass-35), so a call's uploads are spaced a second apart, and a failed upload is tried again after 2, 5 and 10 seconds. Each upload's path, sha256, approval, upload id and every try are on the call's line in `pass-NN.higgsfield.jsonl` and in the take's sidecar; when all four tries fail, the call is refused, with no job and no take counted. Without the field, a list naming a file is refused whole, before any call, and with it a list naming a path outside `approved/`, a link, a URL or anything else still is. The command line runs from a new, empty folder, with telemetry and the update check off;
- **three takes an entry**, counted across the whole job (every pass's `*.higgsfield.jsonl`), per entry and its exact approved wording and test. A job that made nothing and charged nothing is no take;
- **two caps, in credits.** The brief's `higgsfield_credits_cap` for the whole train, and the list's `ceiling_credits` for its test (mc-eng-002: 2,500 for the train, 300 for `sold-proof`); a list whose ceiling is over the train's cap is refused. Each take is priced first by Higgsfield's own estimate (`higgsfield generate cost`, which costs nothing), and refused before any call if it would take the test past its ceiling or the train past its cap, or ask more than the account holds: each is a checkpoint for Sean, and buying more credits is his (never-do 7). The take is then metered from the account's own balance (`higgsfield account status`), read before the call and after it until it moves, up to 90 seconds; a balance that never moves is charged the estimate. The job's line is written the moment Higgsfield takes it, at the estimate, so a call cut off mid-way still counts. One lock makes the job's takes one at a time. The balance is the account's, so anything else spending on it in that window is counted against the job too, which errs toward the cap;
- the take is downloaded the moment it is ready (never-do 13), over https, into a new file in a version folder the pass made in its own stage (`appearance/` for Art, `motion/` for the Animator): `.png`, `.jpg` or `.webp` for an image, `.mp4` for video, by what came back. `<name>.higgsfield.json` sits beside it: the approved entry, the approval, the setup record, the take number, each upload (its path, sha256, approval and upload id), the request as sent, the job, the balance before and after, the credits and how they were measured, the hash, and the label "generated" (never-do 8). Both are created relative to the version folder held open since the check, never through a link and never over a file already there. A take that came back but could not be filed is kept in the pass's scratch folder and counts. Every call, refusals included, is a line in `trace/logs/pass-NN.higgsfield.jsonl`.
- **a charged call is counted, and a made job is filed once** (mc-eng-002's first live call, 2026-10-25). `generate create` answers with a bare list of job ids, which the doorway reads. A call whose answer names no job the doorway can read, but whose balance moved, still counts as a take and its credits, and its line keeps every job id the answer named. `apps.py ask higgsfield --settle <job id> --out <file>` (`higgsfield.py settle`) then files a job this doorway itself started and did not file, read with `generate get` and downloaded, into a new version folder of the pass's own stage, with its sidecar. It is filed as the same take, on a line that stands over the call's own, so nothing is spent or counted twice. A job the doorway never made, one already filed, one of the other kind, or one with no finished result is refused, and nothing is written.

The approved list, `higgsfield.json`:

```json
{"test": "sold-proof", "ceiling_credits": 300, "entries": [
```

## The application doorway

`apps.py` is how a pass gets Blender, Resolve or Krita, on either vendor. None runs inside a seat's sandbox. Both vendors' sandboxes hide the Mac's graphics chip, and neither lets a setting show it (Codex 0.163.0's Seatbelt policy is built in; Claude Code 2.1.303's IOKit list is fixed), so Blender 5.2.2 finds no Metal device and crashes reading its name (exit 139). Resolve's scripting is a TCP link to the running Resolve, which a pass with the network off cannot make. Built on the map's **Blender and Resolve inside the seat sandboxes** ticket (2026-10-19).

- **Who.** A drafting pass whose seat lists the app in [`bench/toolbelts.toml`](../bench/toolbelts.toml) (`apps`): the Director (`blender`, for the animatic in Blender's sequencer), Art (`krita`, on the map's **Krita's doorway** ticket, 2026-10-20), the Animator (`blender`) and Finishing (`resolve`), each writing only its own stage (the map's **Tool ownership** ticket, 2026-10-20, which also dropped the Animator's `resolve`). A gate, an audit or a verification pass gets none.
- **The ask.** The pass runs `python3 -B apps.py ask blender --script <file> [--blend <file>] [-- <args>]`, `ask blender --render --blend <file> --out <folder> --frames S-E [--engine cycles|eevee|workbench]` (below) `ask resolve --script <file>` or `ask krita --script <file> [--fonts <folder>] [-- <args>]` from its shell. That writes a request into `apps/` in its scratch folder and waits up to nine minutes for the result (`apps.py wait <id>` keeps waiting). The script is a `.py` in the scratch folder or a new version folder in the seat's stage. A `--blend` is in the media project.
- **The launcher's side.** While a pass with an app runs, the launcher watches that folder, held open from before the pass started so a link put in its place reads nothing, and runs one request at a time. Each call goes into `trace/logs/pass-NN.apps/`, where no seat writes and every pass reads: the launcher's copy of the script (which is what runs), the lock, the log, the result. Each call is also a line in `trace/logs/pass-NN.apps.jsonl`, and `pass-NN.launch.json` counts them (`apps`), naming any refused and any that wrote somewhere to check. A call counts against the pass's time, and ending the pass ends the call.
- **The lock.** A Seatbelt profile written from the pass's context and run with `sandbox-exec`. It denies by default, as Codex's own base policy does. Reads go as the pass's go (credentials, Sean's Codex home, the employer folders, other skill folders and other scratch folders denied). Writes go only to the fence's folders, and every frozen version folder and artifact is refused after that. No network. **Blender** adds only the graphics chip (`AGXDeviceUserClient`), Metal's shader compiler, the font server and Blender's own caches (`~/.cache/motioncraft/apps/blender` for Cycles' kernels, Metal's per-app cache). It runs `Blender -b --factory-startup --python <copy> -- <args>`. Cycles renders meshes on the CPU or on the graphics chip. A scene holding Grease Pencil does not render under a seat's own script on any engine, and neither does Eevee or Workbench: Blender's GPU drawing engine, which draws Grease Pencil even inside a Cycles render, registers Blender with macOS's app registry (LaunchServices) on start, and the lock refuses that (exit −6).
- **The render request** (ruled on the map's **Grease Pencil renders** ticket, 2026-10-19: open the lock by one rule, behind guardrails, rather than render by hand). `ask blender --render` carries no script and no arguments, only the saved `.blend` (in the media project), the output folder, the frames (at most 2,400) and the engine. The launcher runs its own render script (`RENDER_SCRIPT` in `apps.py`; its copy is in the call's record) under the Blender lock plus one rule, `mach-lookup` of `com.apple.coreservices.launchservicesd`, and nothing else. Blender starts with `--disable-autoexec` before the file loads, so no script the file carries runs (a driver expression, a registered text block); the log's `MOTIONCRAFT_RENDER autoexec_blocked True` says one was there. Cycles renders on the CPU with OSL off, since a script node is code. A kept render is `cycles` into a new version folder in the seat's stage; `eevee` and `workbench` render only into the scratch folder, as previews (Sean, on the same ticket: kept renders stay Cycles on the CPU). What the one rule opens, tested on the Mini 2026-10-19 on a copy of the lock: a process inside can list the running apps (name, bundle id, process id, path) and which is in front. The screen, other windows, the clipboard, posting input and launching an app or a URL stay refused, the last also by LaunchServices itself (`LSOpenCFURLRef` returned −10661 and nothing opened), and the fence, the frozen versions, the credential folders and the network hold as before. Grease Pencil, Eevee and Workbench frames rendered this way matched frames rendered outside the lock pixel for pixel, and repeated across fresh Blender processes. The record is in the private corpus beside the two Blender guides, `runs/blender-5.2.2-2026-10-19/`. **The Director's animatic renders the same way** (the map's **Bench changes from the tool-ownership ruling** ticket, 2026-10-20, mc-setup-015): the render script renders whatever the saved file's output is, so a sequencer edit saved with a movie output (FFmpeg, H.264 with AAC) comes out as one movie file with its sound, `frame-<start>-<end>.mp4`. Tested in the Director's own fence: two boards as image strips over a timing track the seat's script wrote with Blender's sound module (`aud`) rendered into a new version folder, the clicks on their frames, and a second render in a fresh Blender decoded to the same pixels and the same samples, though the two files' bytes differ, which is why TC5 compares decoded frames, never checksums. The render request needed no change.
- **Resolve: the broker.** Anything connected to Resolve can make it run code in its own process, outside every fence (Fusion's `Execute` ran Lua there from inside an earlier lock, 2026-10-19). So the script never reaches Resolve. Its lock opens no port at all, only one local socket, to a broker the launcher starts outside the lock, which alone holds the connection. The script imports a stand-in `DaVinciResolveScript` whose objects forward each attribute and call to the broker. The broker allows only:
  - methods listed in Resolve's own API file (`Developer/Scripting/DaVinciResolveScript.pyi`, read from the installed version), less those that reach Fusion or run code (every method whose name holds `Fusion`, so `Fusion` itself, the Fusion-comp calls, `CreateFusionClip` and the three that put a Fusion title, generator or composition on a timeline; `ValidateDCTL` and `EncryptDCTL`; `AddTransition`, whatever its category, since its `fusion` and `ofx` categories reach Fusion or outside plug-in code (SWCB #257); and `SetFades`, since Resolve 21.1.1 loses a clip's fade on save and reload, so a card's fade is baked into its frames by `ffmpeg` instead (mc-e8.d01, SWCB #262)), change Sean's settings and presets, switch the database, delete, archive or restore projects, touch cloud projects, or quit;
  - work in projects whose names start with the media project's name, and a call that acts on the open project only when that one is the job's own;
  - path arguments given whole and inside the media project or the scratch folder, with a method that writes a file (an export, the render settings) writing only into the pass's fence;
  - a project, timeline or bin file, a grade file or a LUT in a version folder (any stage's, `approved/` included) or in the pass's fence loaded only as Resolve itself exported it through the doorway, by the export register below, in this pass or an earlier one; never one a pass wrote, frozen since or not (a project file can carry Fusion compositions, and so code; see the grade-file finding below). One elsewhere in the media project, such as Sean's `inputs/`, loads as it is;
  - rendering started only when every render job's target folder is inside the fence, and a quick export only with its target named.

  Every call and refusal goes to `<id>.calls.jsonl`.
- **The export register** (Sean's route on SWCB #264, 2026-10-22). An earlier version's `.drp` is how a version reopens without Resolve's own project database, but a pass may have written that file by hand before its version was frozen, and freezing proves only that a file has not changed since, not who made it. So the broker records what Resolve itself wrote. On an export that a later call may load (`ExportProject`, a timeline's or a bin's `Export`, `ExportStills`, `ExportLUT`, `ExportCurrentFrameAsStill`), it has Resolve write into the call's own folder (`~/.cache/motioncraft/apps/resolve/calls/<id>/`, which no pass can reach, deleted when the call ends), then adds a line for each file Resolve wrote to the machine's export register (`~/.cache/motioncraft/apps/resolve/exports.jsonl`: the sha256, size, file, method, project, pass and engagement), and only then copies the file to where the script named it. A pass that rewrites the file while Resolve writes it changes only its own copy. An export Resolve reports as failed records nothing. On a load, the broker reads the file without following a link, and refuses it unless its sha256 is in the register. A path that runs through a pass-writable folder, as named or once its links are resolved, is checked this way wherever a link in it points; any other path reaches Resolve resolved, in a folder no pass writes, so nothing can be repointed between the check and the load. Then it hands Resolve its own copy of the bytes it checked, so nothing the pass does to its file after the check reaches Resolve. A byte-for-byte copy (an approved copy, a version copied forward) loads wherever it sits, and a changed one never does. The register is per machine: a version exported on the Mini reopens through the doorway on the Mini, and anywhere else a person imports it by hand. Each call's log names what it exported and what it loaded (`exported`, `loaded`), each with its sha256. **Fusion is closed for every seat** (ruled on the map's **Fusion through the doorway** ticket, 2026-10-19). Resolve's API sets fixed values only (opacity, blend modes, position, zoom, crop, rotation, the grade) and cannot keyframe them, so anything that moves is animated in Blender, and Resolve stacks, cuts, grades and delivers. A pass that needs what only Fusion can do stops on the reopen rule in the [master skill](../../.claude/skills/motioncraft/SKILL.md); a slice of Fusion opens only on its own ticket, with refusal tests.
- **Grade files and LUTs (checked 2026-10-19, Resolve 21.1.1 on the Mini).** A `.drx` grade file (`ApplyGradeFromDRX`, or a gallery's `ImportStills`) is XML around the grade itself, one compressed binary blob (zstd) of the node graph that names each node's tools: a LUT applied with `SetLUT` showed up inside it by name. The doorway cannot read that blob, and a colour node can hold a DCTL, which is code run in Resolve, or ResolveFX; so it is treated as a project file is, loaded from a version folder or the fence only as Resolve exported it. `SetLUT` with an absolute path outside Resolve's LUT folders failed for a `.cube` and a `.dctl` alike (Resolve applies only LUTs it has discovered there, which no pass can write), and a LUT named from the top of that folder worked; a pass-written path is refused anyway, so a later Resolve that loosens this changes nothing. A pass may still apply a grade Resolve exported (a gallery's `ExportStills`) or one Sean saved in the project's `inputs/`, and name a LUT at the top of Resolve's LUT folder (one in a subfolder, such as `Film Looks/`, needs a relative path with a `/`, which the path rule refuses today).
- **Resolve's own writes.** Resolve still writes its database, caches and renders from its own process. For each Resolve call the doorway records every path written on the Mac (FSEvents) and sorts it as in the fence, Resolve's own folders, frozen, the launcher's record, or outside. Afterwards it asks Resolve itself for its database, open project and render targets. The check record lists anything outside the fence. FSEvents names no process, so another program writing in that window shows there too.
- **Krita, with no screen** (built on the map's **Krita's doorway** ticket, 2026-10-20, mc-setup-016). The launcher runs `kritarunner -s motioncraft_krita -f main` with Qt's offscreen platform. `motioncraft_krita` is the launcher's wrapper (`KRITA_WRAPPER`), written into the call's record and put on Krita's Python path with `PYTHONUSERBASE`, since kritarunner ignores `PYTHONPATH`. It runs the seat's script as `__main__` with its arguments and ends with `MOTIONCRAFT_KRITA done <code>`. kritarunner exits 0 when a script fails to load, so a call is ok only when that line says 0.
  - **What works:** layers, their order, blend modes and opacity, Krita's filters, `.kra`, `.ora` and `.psd` saves, each layer as a PNG with transparency (`Node.save`), and a flattened PNG from `Document.pixelData` through a `QImage`. `Node.save` returns nothing and bakes the layer's opacity into the PNG's alpha, so a layer handed on with its opacity stated is exported at 255 and its opacity restored (found by the Director's review on E7, mc-e7, 2026-10-20). A reopened `.kra` re-exports to the same decoded pixels.
  - **What does not:** Krita's brush engine. `Node.paintLine`, the other `paint…` calls and `paintAbility` read the main window's active view with no null check, and every way to open one with no screen crashed. kritarunner never loads Krita's built-in GUI resources, so `addView` (or showing the window) fails on a toolbar menu that was never built, after the welcome page's news set-up (under the "C" locale) and the clipboard set-up (Qt's offscreen clipboard starts empty) were got past. The full Krita app crashes at the clipboard while building its first window, before any Python plugin loads. `Document.exportImage` stalls with no screen, lock or no lock. **Text** works: Krita's own SVG text on a vector layer, shaped by its HarfBuzz, from a font file registered first with Krita's own Fontconfig (`FcConfigAppFontAddFile` through its bundled `libfontconfig`). A font file copied into the call's Krita folders is never seen, since Krita reads them only at start-up, and Krita substitutes with no error (E8, SWCB #256). So the launcher does the registering (the next point). Sean chose to build the doorway without the brush engine: Art draws its strokes with Qt's painter (`QPainter` on a `QImage`) and sets them on a layer (`setPixelData`). The other options he weighed, the full app on the Mini's screen, a Qt display plugin with a working clipboard, and Grease Pencil, are in the ticket's evidence comment.
  - **A version's fonts** (Sean's call on SWCB #263, 2026-10-22). `ask krita --fonts <folder>` names a folder in the media project, the version's `assets/fonts/`. The launcher takes every `.otf`, `.ttf`, `.otc` and `.ttc` in it and below (a licence beside them is left alone; a link, or a file reaching outside the media project, is refused; at most 64), copies them into the call's home, and records each by its path and the copy's checksum. Before the seat's script runs, the wrapper hands each copy to the Fontconfig configuration Krita's text library made (`FcConfigAppFontAddFile`), and prints the families they hold, which the result and record carry. Then, in every call, with `--fonts` or without: text added with `addShapesFromSvg` that names a family the call did not register, or names none, is refused before Krita makes it; a document opened with `openDocument` that holds such text is refused once open, before the script gets it; and every document still open at the end is read once more. Each refusal is printed to the log and fails the call, even if the script caught it. Generic families (`serif`) count as unregistered, so a fallback list fails too. Tested on the Mini with STIX Two Text, which Krita's own Fontconfig cannot see unregistered: unregistered, a reopened card comes out in a substitute; registered, it re-exports to the same decoded pixels.
  - **A home of its own per call.** kritarunner keeps its settings, resources (about 110 MB, a database rewritten every run) and caches under the name `kritarunner` in the home folder, and its resource folder is on its Python path, ahead of the wrapper. So a call never runs in Sean's home. The first Krita call on a machine starts Krita once, with no seat code, in an empty folder under the call's lock, and keeps the result as that Krita version's template (`~/.cache/motioncraft/apps/krita/template-<version>/`). Each call then runs in an APFS clone of it (`calls/<id>/`), deleted when the call ends, so a pass cannot leave a module or setting for a later pass. `CFFIXED_USER_HOME` points macOS's own folder lookups there; `HOME` covers Qt and fontconfig. Sean's own `kritarc` and `krita/` folder are never written.
  - **The lock** adds only the call's home and the font server: no graphics chip, no window server, no LaunchServices, no network. One more opening was needed. Krita saves through a hidden copy named `.XXXXXX.<ext>` in the Mac's own temporary folder (`/var/folders/…/T/`), which Qt uses whatever `TMPDIR` says, and a refused copy makes the save wait for ever. The lock allows writing only that name shape there (Seatbelt regexes take no `{n}` counts, so one or more letters or digits). Krita's tile swap file would also land there, or in the folder named at the template's first start; each call's settings point it into its own home (`swaplocation`).
- **Before a Resolve call** the coordinator opens Resolve on the machine, with nothing of Sean's unsaved: `CreateProject` and `LoadProject` switch the open project.

## Filing a pass's logs

`filing.py` runs at the end of every launched pass, before the record is written, and by hand on logs filed before it existed (`filing.py <engagement> [--pass pass-NN]... [--check]`). Built on the map's **Launcher: strip embedded frames and employer paths from pass logs at filing** ticket (SWCB #245), from the frame-log ruling (SWCB #240) and Sean's ruling on E7 (2026-10-20).

- **Images and sound out.** A pass that opens an image carries it whole in its log. Claude Code writes the picture it read into the tool result, as a JPEG it may have shrunk, twice on the line. Codex writes each image it viewed into the tool's output as a data URL, after an image-view event naming its path. Each becomes one line: `motioncraft-stripped`, its type, the sha256 and size of the copy removed, the path the log shows, and, when that path is a file in the media folder, the file's own sha256 and size. A path outside the media folder is marked not kept, and an image with no path shown keeps its sha256 alone. No unstripped copy is kept; the frames live in the media folder.
- **The employer folders out.** Every path on the machine's employer-path list becomes `<employer folder>` in every file the step files, in its plain, `~`, `file://` and percent-encoded forms, and only as a whole path: a longer folder name beside it is left as it is. Where that changes a doorway lock or script copy, its call log gets `filed_sha256` beside the sha256 it recorded.
- **The refusal.** The step then reads every file again. Any image, sound or employer path left, or any file it cannot read as text, is named, the launch exits 4 with `filing refused` in its outcome, and nothing from that pass may be committed. The record's `filing` field gives the counts. Filing twice changes nothing.
- **The trace kit reads the filed logs as it read the originals.** On E7's logs, the rung-0 checker gave the same result on every line before and after filing, line 11 included (the runtime stamps and helper catch, on Claude logs and Codex rollouts alike).

## Freezing versions

The source contract's § 4 says a finished version gets `checksums.sha256` last and is then made read-only, files and folders, and is never unfrozen. On the first film only the approved copies were ever locked: nine superseded versions (162 folders, 3,888 files) stayed writable to the Close, and the four exercise approved copies held 40 writable folders, because a copy made with `cp -R` keeps each file's read-only bits and gets fresh writable folders; the Close checklist read `approved/` alone and never saw it (mc-self-001, finding SC9; SWCB #258). The exposure was never a seat pass, whose fence freezes every earlier version, but the coordinator, Sean's own tools and the Finder. So:

- **`launch` freezes what a pass made.** After the version check, each version with its three files is read again: its `checksums.sha256` re-taken (every listed file there and matching) and compared with the folder (no file left unlisted, the list itself excepted), and no link inside. A version that passes is made read-only, every file and folder, write bits off and the other bits kept, and its line in the record's `versions` says `"locked": true` with the checksum counts. One that fails is refused like a missing manifest: `version refused: <version> checksums.sha256 does not verify (<file> differs)`, or `holds files not in checksums.sha256 (<files>)`, or `holds a link (<path>)`, or `could not lock (...)`; exit 5, `"locked": false` and `refused` in its line, and the folder left exactly as the pass left it, so its seat can see what it did. A pass is told this in its prompt, so it finishes a version before it stops. Versions already in the stage when the context was written are the fence's, untouched here.
- **`freeze.py sweep <project>`** lists every version folder in a media project (each folder directly inside `story/`, `appearance/`, `motion/`, `finish/` and `approved/`), with its three files, what is writable by mode bits (folders and files, counted separately) and its checksums re-taken; `--json` gives the rows. Exit 0 only when every version is locked and every list verifies. The Close checklist runs it, and a refusal there is a finding, never something to fix by hand.
- **`freeze.py lock <project> [--version STAGE/NAME]...`** locks every writable version (or the ones named) whose checksums verify and that holds no link, and refuses the rest by name, left as they are; a version without a `manifest.md` (every October version, made before SWCB #249) is locked all the same, its gap printed. Exit 1 on any refusal. This is how an approved copy is locked after it is made, and how the exercises' remaining folders were locked on 2026-10-21.
- **Mode bits, never `os.access`.** The Codex reviewer on the self-check found that `os.access` asks whether the calling process may write, which from inside a read-only sandbox reads zero writable paths whatever the bits say; the self-check's first count was wrong for that reason (N1). Everything here reads `st_mode`, and links are never followed.

## The seat probe

`seat.py seat-probe` runs one probe pass per seat on its real launch form, in a throwaway job, and asks it to list its tools, read each of its toolbelt's skills, and try to read a skill outside it. The verdict comes from what the vendor reports, not the answer: on Claude, the log's first line (tools, skills, plugins, connectors, model), against a bare baseline run that lists Claude Code's own built-in skills; on Codex, the session file's state (no skills, plugins, apps or `AGENTS.md` offered), the rendered prompt, the seat home and pass layer (no connector), and the stamp. The answer's own lines are checked too: the toolbelt read, the outside skill blocked, and, where the corpus is on the machine, one guide opened by its lane pointer (`../corpus/guides/<first guide>`) as the prompt's library note resolves it, its `title:` line printed back (SWCB #250). `--read-only` runs a seat in its audit form, the form whose passes could not find the library in mc-eng-001.
